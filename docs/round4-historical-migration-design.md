# 第四轮：超大合法旧库分页迁出与分阶段恢复

## 真实边界调查

原始740b98b的importCard没有整库数量/字节限制，故2001卡及超过40MiB的历史库都可能合法存在。原单卡入口parseJSON限制2MiB UTF-8，validateCard限制16层、50,000值并使用正式Schema；64个19,000字节子节点组成的约1.2MiB卡是合法大卡。本轮不将历史合法库重新定义为损坏，也不把正式Schema可表达但旧导入器会拒绝的>2MiB手工注入记录冒充历史正常导入。

第三轮总40MiB是序列化分卷文本+清单总量（另有cards JSON+reading预留预算），不是IndexedDB原始占用，也不是浏览器硬上限。旧exportVolumes先toArray三表、构建所有卷字符串；restoreVolumes先读所有文件、拼接全部记录，因此只增大常量会同步扩大峰值。该旧路径及其测试保留，新路径不调用它的整库组装逻辑。

依赖关系不变：reading.cardId→storedCard UUID，reading.nodeId→同卡完整树，settings.lastCardId→全局某卡；正式Card无跨卡ID字段，source URI没有应用解析的外键语义。卡片树不分拆，状态跟随所属卡，最后阅读引用在最终整套校验后保留。原主数据库version1三表完全不升级；暂存使用独立数据库，取消/清理暂存不删除原库。

## 独立入口与实际用户流程

普通阅读器仍会加载整库，因此大库应直接使用本候选的 **migration.html**，无需先进入普通阅读界面。该专页不读取全部卡片来渲染列表。原阅读器增加静态入口链接，其字体/焦点/内容实现不重写。

1. 在持有原数据的同一浏览器、同一网站来源打开候选migration.html。勿清除网站数据。
2. 选择“准备分页迁出”：只读一致性快照，按4条记录批次读，按最多500卡/8MiB生成完整v1卷，逐卷写入独立暂存；全部源快照读取提交成功后才发布完成清单。
3. 逐卷下载及保存完成清单。下载分页只展示20个卷按钮，每次读取一个卷，不把所有字符串/Blob放在页面内存。
4. 若浏览器暂存空间不足，支持File System Access目录写入的桌面Chromium可选“直接导出到本地目录”。它用同一快照/校验/分卷算法，逐文件写用户选择的本地目录，**不复制任何卷/整库到浏览器迁移暂存**。只有最后完成清单发布才表示全套完成。目录必须有足够空间，文件未加密。
5. 恢复可在原站或有充足空间的新浏览器中完成，**无需先清空原数据库**：先选分页完成清单，再按批选择分卷。缺卷时保持working，已验证卷存在独立暂存，可关闭/刷新后从“继续暂存”打开。相同内容重复卷幂等，不同内容重复卷拒绝。
6. 所有卷及全局链/总数/字节/引用/唯一性通过才ready；明确确认后一个主库三表readwrite事务原子替换。逐批从暂存读4条，不拼接整库。全部提交后才显示成功。
7. 原始文件请保留；清理迁移暂存只影响独立工作区。普通阅读器的大库交互不是本轮扩展范围，不承诺无限大库阅读性能。

## 新包装清单与完整性

Card协议与v1备份envelope不变。每卷仍是 `{version:1,checksum,payload}`。新增的是另一种**包装清单** `mindflow-paged-transfer/version1`，与第三轮小型transfer-set并存，旧单卷/分卷读写均不改变。

清单恒定大小（解析上限16KiB），记录setId、原settings、totalCards、totalParts、totalBytes、chain和checksum，不枚举所有卷。totalBytes为数据卷UTF-8字节之和，不含恒定大小的清单；每卷8MiB限制包含整个v1 envelope。卷名由setId和连续序号确定。链初值绑定kind/setId/settings，每卷递推绑定前链、序号、文件名、完整文本checksum、卡数和字节数，最终值必须等于清单。checksum使用现有canonical-JSON SHA-256助手；文件文本作为JSON string进行canonical hashing，空白变化也会改变链。它不等同于raw-file sha256sum，也不提供认证/加密。

准备恢复时先校验清单自身checksum。每卷检查大小、正式协议、每卡hash、完整reading及卷内引用，并在暂存事务内通过索引验证跨卷UUID/hash唯一性；最后核对总数/总字节/最终链和全局lastCardId。乱序选中的一批文件按序号处理；缺失下一卷不能跳过，额外/混集文件不被静默忽略。全套修改并重新计算所有无密钥hash不是本格式防护的攻击模型。

## 原子性、刷新和空间不足

- 导出在主库readonly事务内读取快照，期间其他写入排队。hash及跨库/本地文件异步IO用Dexie.waitFor维持事务；没有等待用户逐个下载来长时间占用源事务。清单在快照完成后才发布；取消/关闭/失败只留下未完成缓存/文件，不能伪装完成集合。未完成快照需重新导出，原库不删。
- 恢复每卷暂存事务独立提交，仅写工作区。主库尚未改变；刷新后读取进度继续选卷。
- 提升使用**一个**主库cards/reading/settings事务；通过Dexie.waitFor读取另一个数据库的小批次，维持目标事务。每批再次验证暂存内容hash/标识/引用，任何错误、QuotaExceededError、取消或关闭都会回滚主库事务。并非逐批提交到主库。
- 完成提交与工作区“complete”标记不是跨库原子提交：如果在主库成功后、标记前关闭，主库是完整新库，工作区可能仍ready。启动不会自动提升；用户先检查当前库，再选择保留/丢弃暂存或显式重新恢复。不会将状态不确定的提升自动重做。
- 暂存满时原库/已验证卷保留，腾出**其他迁移暂存**或使用有空间目标后重试；不得先删除唯一原库。直接目录导出可绕过浏览器工作区不足，但不能绕过本地目录磁盘不足。

## 容量承诺与资源风险

新分页路径不设2000卡、40MiB总量或16卷硬门槛；计数受JavaScript安全整数和真实存储资源约束，而不是通过扩大旧常量实现。每卡历史2MiB/16层/50,000值不变；每卷500卡/8MiB不变；源/目标批次最多4条，清单恒定大小，唯一性与进度存储在磁盘索引，不创建整库Set/数组。UI文件按次/批读，不能一次把全部File.text读入。

JavaScript工作集由一卷+最多4条记录及序列化/校验表示组成；这**不证明原生浏览器进程或事务日志恒定内存**。IndexedDB后端原子写入可能使用随库规模增长的日志/磁盘/原生缓存；长事务和系统杀进程仍需平台实测。单次外部IO60秒保护超时不改变数据完整性，超时明确失败不发布完成清单/不提交目标。没有固定sleep实现正确性。

实际压力：数量501/2000/2001；字节独立near40/over40大卡；真实Chromium另用2001卡、49,424,718字节（约47.14MiB）同时跨两个旧边界。每卷观测<8MiB、每批4条，阶段JS堆样本写入公开日志。这些是已测规模，不是无限数据/所有设备保证。硬盘、配额及浏览器事务限制仍可能失败；失败必须保留原数据和文件。

## 极端环境的可执行保全与未解决风险

- 有目录API且原库仍可读：从独立入口直接写有足够空间的本地/外接目录；在另一有空间的同候选浏览器先暂存验证、确认后恢复。无需清空原站或上传私人内容。核心sink已以真实本地文件IO往返测试；真实桌面文件选择授权UI未做人工走查。
- 无目录API且没有暂存配额：先删除可确认无用的迁移工作区缓存（不删主库），保留网站数据后重试；不要通过清除整个网站数据“腾空间”。若仍不能迁出，本轮**不能声称此组合已解决**。
- 桌面还可在浏览器完全退出后，依其官方profile位置说明复制整个User Data/profile及相关本机状态到安全本地磁盘作为保全副本，再在独立副本/足够空间环境寻求支持。副本可能包含敏感凭证，应离线保护、不要上传。本方案是非破坏性保全，不等于已验证的Mindflow JSON迁移或跨OS可移植恢复。
- Safari/iPhone、无目录API且不可腾配额、无法取得配置文件的环境，仍没有本轮已验证的极端库迁出路线。该资源/平台组合保留兼容风险，不重新定义历史数据为非法，不宣布“全部旧库兼容”。真实iPhone、系统终止、线上SW升级等继续NOT VERIFIED。

## 测试和初次诊断的记录

新压力用例首轮把通用5秒断言用于仍在运行的约47MiB导出（实际已完成1336/2001卡），因此失败。改为等待该新任务的可观察完成/取消控件消失，再保留所有清单、字节、数量、hash、提交和回滚断言；新压力任务总预算120秒/单操作60秒，原测试的超时/断言不改，无固定sleep。

第二次故障注入把`.onsuccess`赋值后又被Dexie覆盖，并过早锁住暂存库，使目标clear时点标记未出现。改用独立addEventListener，并在目标clear成功后加真实暂存写锁，再刷新验证回滚。没有修改生产代码来绕过此测试，也没有删除故障场景。最终压力结果和阶段样本见本轮原始日志；初次诊断不冒充产品通过证据。
